# 宿舍零食上门微信小程序——整体产品设计方案

- 文档版本：V1.0
- 编写日期：2026-10-23
- 产品阶段：概念验证 / MVP 规划
- 暂定产品名：**宿舍补给站**

---

## 1. 项目概述

### 1.1 项目背景

大学宿舍通常存在晚间出入受限、校外配送难以进入、临时购买零食和日用品不方便等问题。与此同时，一些学生愿意提前囤货，并面向本栋或附近宿舍提供小范围销售和配送服务。

本产品拟搭建一个校园内的轻量化供需撮合平台：

- 学生商家可以申请入驻并开设自己的宿舍小店；
- 商家可以维护分类、商品、价格、库存、图片、营业时间和配送范围；
- 普通学生可以浏览本楼栋可服务的小店并提交订单；
- 小程序首期不提供在线支付，订单作为预订和履约凭证，双方在交付时线下完成付款；
- 平台提供订单、库存、通知、评价、投诉和运营管理能力。

### 1.2 产品定位

> 面向大学校园宿舍场景的“同楼即时零售信息与履约平台”。

产品不是传统外卖平台，而是围绕“距离极近、客单价低、夜间需求强、库存有限、交付灵活”的宿舍场景进行设计。

### 1.3 核心价值

#### 对购买者

- 晚间无法出楼时也能快速买到零食和应急用品；
- 可看到真实库存，减少反复询问；
- 下单时直接说明楼栋、楼层、房间和交付方式；
- 能查看订单进度并与商家沟通。

#### 对商家

- 低成本开设宿舍小店；
- 统一管理商品、库存和订单；
- 明确服务范围和营业时间；
- 沉淀复购用户和经营数据。

#### 对平台

- 聚合校园内分散的小规模供给；
- 通过审核、规则和信用体系降低交易风险；
- 后续可扩展服务费、推广位、商家工具等商业模式。

## 2. 产品目标与边界

### 2.1 MVP目标

首个版本只验证三个核心问题：

1. 是否有学生愿意通过小程序向同楼商家下单；
2. 学生商家能否稳定接单、管理库存并完成交付；
3. 平台能否在不接入在线支付的情况下形成可持续的订单闭环。

### 2.2 MVP建议范围

首期建议聚焦：

- 一所学校；
- 一个校区；
- 3～5栋宿舍楼；
- 同楼配送或指定楼栋配送；
- 预包装食品、饮料和低风险日用品；
- 线下付款；
- 人工审核商家；
- 平台人工处理投诉。

### 2.3 首期暂不支持

- 在线支付、分账、提现；
- 跨校交易；
- 校外骑手配送；
- 拼团、秒杀、优惠券等复杂营销；
- 自制食品、散装食品、现制饮品、酒类、烟草、药品等高风险或强监管品类；
- 多规格、多仓库、复杂进销存；
- 自动退款和平台担保交易；
- 商家之间调货。

控制首期范围非常重要。建议先把“找店—下单—接单—交付—完成”跑通，再增加营销和商业化功能。

## 3. 用户角色

| 角色 | 主要目标 | 主要能力 |
|---|---|---|
| 购买者 | 快速找到可配送的商品并下单 | 选校区/楼栋、浏览店铺、购物车、下单、查看进度、取消订单、评价、投诉 |
| 商家/店主 | 开店、卖货、管理订单和库存 | 入驻申请、店铺设置、商品管理、库存管理、接单/拒单、配送、经营数据 |
| 店员（后续） | 协助店主处理订单 | 接单、备货、配送，不可修改结算和店铺主体信息 |
| 平台运营 | 管理商家、商品、订单和风险 | 审核、上下架、封禁、投诉处理、公告、数据看板、内容配置 |
| 校园/楼栋运营人员（后续） | 负责某个校园或楼栋的线下运营 | 商家拓展、现场核验、异常处理、活动运营 |

一个微信用户可以同时是购买者和商家，但进入商家工作台前必须完成入驻审核。

## 4. 核心业务规则

### 4.1 店铺服务范围

每个店铺需要设置：

- 所属学校、校区、宿舍区、楼栋；
- 可服务楼栋；
- 可服务楼层；
- 配送方式：送到寝室门口、送到楼层公共区域、送到一楼、自取；
- 营业时间；
- 最低起送金额（可为0）；
- 配送费（首期建议为0或固定金额）；
- 预计送达时间；
- 临时休息和打烊状态。

MVP不要求购买者预先选择学校或楼栋。商家可通过店铺公告说明服务范围，购买者仅在提交订单时填写具体送达位置。建议商家主要服务本楼或附近宿舍，以提高履约效率并减少进入限制和安全问题。

### 4.2 店铺可见性

购买者通过商家分享卡片直达店铺，或在首页按店铺名称搜索。搜索结果只显示：

- 店铺名称或公告与搜索词匹配；
- 已审核通过；
- 未被平台封禁；
- 当前有可售商品的店铺。

店铺卡片展示：营业状态、预计送达时间、最低起送金额、销量、评分和主营品类。

### 4.3 商品规则

商品基础字段：

- 商品名称；
- 分类；
- 主图和详情图；
- 售价；
- 参考原价（可选）；
- 当前库存；
- 每单限购数量；
- 商品状态：草稿、上架、售罄、下架、违规下架；
- 保质期或到期日提醒（建议支持）；
- 商品描述；
- 规格属性（后续版本支持）。

首期建议一个商品只对应一个价格和一个库存单位。例如“可乐500ml”和“可乐330ml”分别创建商品，避免过早引入复杂SKU。

### 4.4 下单规则

购买者下单时填写或确认：

- 楼栋；
- 楼层；
- 房间号或约定地点；
- 联系方式；
- 交付方式；
- 订单备注；
- 付款方式提示，如现金、微信当面转账等；
- “本订单由买卖双方线下收付款”的确认提示。

下单前再次校验：

- 店铺是否营业；
- 地址是否在服务范围；
- 商品是否上架；
- 商品库存是否充足；
- 是否达到起送条件；
- 是否存在未处理的恶意下单限制。

### 4.5 库存处理

为避免超卖，建议采用“可用库存 + 锁定库存”的方式：

1. 用户提交订单成功后，系统原子性锁定库存；
2. 商家拒单、接单超时或用户在允许阶段取消，释放库存；
3. 商家接单后，库存继续保持锁定；
4. 订单完成后，锁定库存转为已售数量；
5. 异常关闭时按平台规则决定是否恢复库存。

示例：现有库存10件，用户下单2件后，可用库存变为8件、锁定库存为2件。

### 4.6 商家接单

- 商家收到新订单提醒；
- 建议接单时限为3～5分钟；
- 商家可以接单或拒单，拒单必须选择原因；
- 超时未处理则自动关闭订单并释放库存；
- 商家接单后展示预计送达时间；
- 如商品临时缺货，商家应拒单，不建议私自替换商品。

### 4.7 取消规则

- 商家接单前：购买者可直接取消；
- 商家接单并开始备货后：购买者提交取消申请，由商家确认；
- 已开始配送后：原则上不可单方面取消，可通过协商处理；
- 已完成订单：不可取消，只能发起售后或投诉记录；
- 高频取消、恶意下单用户可被限流或暂时禁止下单。

### 4.8 线下付款说明

首期平台不处理资金，但仍要记录订单金额和付款状态：

- 待线下付款；
- 买家已付款；
- 商家确认收款；
- 存在付款争议。

建议在交付时由商家点击“确认交付”，购买者点击“确认收货”，并提示双方在线下完成付款。若购买者长时间不确认，可在一定时间后由系统自动完成，但要保留投诉入口。

需明确：**不接入在线支付不代表平台和商家可以忽略食品经营、消费者权益、个人信息和校园管理方面的要求。**平台上线前应结合当地监管要求和学校规定进行审核。

## 5. 核心业务流程

### 5.1 购买者流程

```text
首次进入
→ 微信登录
→ 同意隐私规则
→ 搜索商家告知的店铺名称，或打开商家分享卡片
→ 进入指定店铺
→ 进入店铺查看商品
→ 加入购物车
→ 确认商品、地址、交付方式和备注
→ 提交订单并锁定库存
→ 等待商家接单
→ 商家备货
→ 商家配送/用户自取
→ 线下付款
→ 确认收货
→ 评价或投诉
```

### 5.2 商家入驻流程

```text
进入“我要开店”
→ 查看入驻要求和禁售清单
→ 实名认证/学生身份核验
→ 填写学校、楼栋和店铺信息
→ 提交所需资质与承诺材料
→ 平台审核
→ 审核通过
→ 设置营业时间和配送范围
→ 创建分类和商品
→ 商品上架
→ 正式营业
```

审核状态包括：草稿、待审核、补充材料、审核通过、审核拒绝、暂停营业、封禁。

### 5.3 商家履约流程

```text
收到新订单
→ 查看库存和配送信息
→ 接单或拒单
→ 接单后开始备货
→ 标记“配送中”或“待自取”
→ 到达约定地点
→ 线下收款并交付
→ 商家确认交付
→ 用户确认收货
→ 订单完成
```

### 5.4 投诉处理流程

```text
用户提交投诉
→ 选择问题类型并上传证据
→ 平台冻结相关评价/标记风险订单
→ 联系双方核实
→ 平台给出处理结果
→ 警告、商品下架、限制接单、暂停店铺或封禁账号
→ 形成风控记录
```

由于平台首期不经手资金，平台不能直接在线退款，但可以要求双方协商、记录处理结果，并对违规商家采取平台治理措施。

## 7. 关键页面产品说明

### 7.1 首页

首页建议包含：

- 顶部当前学校、校区和宿舍楼；
- 营业状态提示；
- 搜索框；
- 运营公告；
- 常用分类，如膨化食品、饮料、泡面、甜品、生活用品；
- “最快送达”“同楼热卖”“新开小店”等店铺分区；
- 店铺列表；
- 最近购买入口。

首页的首要目标不是展示大量内容，而是让用户输入商家告知的店铺名，或通过分享卡片直接进入指定店铺。

### 7.2 店铺详情

店铺页包含：

- 店铺名、头像、公告；
- 营业状态、营业时间；
- 预计送达时间；
- 服务楼栋和交付方式；
- 商品分类导航；
- 商品列表、库存和销量；
- 购物车悬浮栏；
- 商家资质/平台审核标识；
- 评价与投诉入口。

### 7.3 确认订单页

必须突出展示：

- 当前店铺；
- 商品明细、数量和小计；
- 地址与交付方式；
- 联系方式；
- 订单备注；
- 商品总额、配送费和应付总额；
- “线下付款，平台不代收款”的说明；
- 预计送达时间；
- 提交订单按钮。

### 7.4 商家工作台

首页用数据卡片呈现：

- 当前营业状态；
- 待接单数量；
- 配送中数量；
- 今日订单数；
- 今日成交额（仅统计订单记录，不代表平台已收款）；
- 低库存商品数量；
- 待处理投诉数量；
- 快捷操作：接单、上商品、补库存、打烊。

新订单需要有明显声音或震动提醒，但要允许商家关闭。

## 8. 订单状态设计

建议订单状态如下：

| 状态码 | 状态名称 | 操作方 | 说明 |
|---|---|---|---|
| CREATED | 待接单 | 商家 | 已锁库存，等待商家处理 |
| ACCEPTED | 已接单/备货中 | 商家 | 商家确认可以履约 |
| READY | 待自取 | 商家 | 自取订单已备好 |
| DELIVERING | 配送中 | 商家 | 商家正在配送 |
| DELIVERED | 已交付待确认 | 用户 | 商家已交付，等待用户确认 |
| COMPLETED | 已完成 | 系统/用户 | 交易履约结束 |
| CANCEL_REQUESTED | 申请取消 | 商家 | 接单后用户申请取消 |
| CANCELED | 已取消 | 系统/用户/商家 | 释放库存 |
| REJECTED | 已拒单 | 商家 | 释放库存并记录原因 |
| TIMEOUT_CLOSED | 超时关闭 | 系统 | 商家未及时接单 |
| DISPUTED | 争议中 | 平台 | 投诉或付款争议处理中 |
| CLOSED | 已关闭 | 平台 | 异常订单结束 |

订单还应分别记录：

- 履约状态；
- 付款记录状态；
- 售后/投诉状态。

不要用一个字段承载所有状态，否则后续很难扩展。

## 9. 商家与商品治理

### 9.1 商家审核建议

平台至少收集并审核：

- 真实姓名和联系方式；
- 微信实名认证状态或其他实名材料；
- 学生身份或校园身份；
- 所属校区、宿舍区、楼栋；
- 店铺经营者信息；
- 经营范围；
- 所需的许可、备案或证明材料；
- 食品安全和平台规则承诺；
- 学校允许开展相关活动的证明或确认（如学校要求）。

具体需要哪些证照，不应仅凭产品设计判断，应在试点地区由专业人士结合经营品类、经营方式和当地监管口径确认。学生身份本身不能替代食品经营许可或仅销售预包装食品备案；如果商家无法提供依法要求的材料，不建议允许其上线经营。

按照2026年5月20日起施行的网络食品销售新规进行产品预留：商家实名和资质信息至少每6个月复核一次，登记与审查档案至少保存2年；网络食品订单信息自交易完成之日起至少保存3年。平台还应具备食品安全管理责任人、风险清单、违规处置和投诉举报机制。具体适用方式以主管部门意见为准。

### 9.2 建议首期允许销售

在资质和学校规则允许的前提下，优先考虑：

- 有完整包装和标签的零食；
- 瓶装或罐装饮料；
- 方便面、自热食品等预包装食品；
- 纸巾、湿巾等低风险日用品；
- 文具、充电线等宿舍应急用品。

### 9.3 建议首期禁止销售

- 烟草及电子烟；
- 酒类；
- 药品和医疗器械；
- 管制器具；
- 易燃易爆品；
- 三无产品、过期食品；
- 自制、散装或来源不明食品；
- 需要特殊温控但无法保障储存条件的商品；
- 成人用品等学校或平台限制品类；
- 其他法律法规、微信规则或学校制度禁止的商品。

### 9.4 商品审核机制

MVP可采用“商家发布 + 运营抽检”：

- 商品名称和描述进行敏感词、禁售词校验；
- 新商家前若干个商品人工审核；
- 高风险分类全部人工审核；
- 用户可举报商品；
- 平台可直接下架并要求整改；
- 保留商品修改和上下架操作日志。

## 10. 信用、评价与风控

### 10.1 评价体系

用户在完成订单后可评价：

- 商品是否一致；
- 配送速度；
- 服务态度；
- 文字评价；
- 图片凭证；
- 匿名评价。

只有真实完成订单的用户可以评价。商家可以回复，但不能删除评价。平台可以隐藏违法违规、辱骂或泄露个人信息的内容。

### 10.2 商家信用指标

- 接单率；
- 平均接单时间；
- 平均送达时间；
- 商家取消率；
- 投诉率；
- 商品缺货率；
- 好评率；
- 违规次数。

### 10.3 用户风险指标

- 下单后取消率；
- 拒收次数；
- 虚假投诉次数；
- 同设备或同账号异常下单；
- 短时间大量下单；
- 频繁更改联系方式和房间信息。

### 10.4 风控措施

- 新用户单笔和每日订单限制；
- 高风险用户限制货到付款下单次数；
- 商家可将恶意用户加入店铺黑名单，但需允许平台复核；
- 平台可以警告、限流、暂停下单、暂停接单或封禁；
- 重要操作保留审计日志；
- 对商家和用户展示必要信息即可，不公开完整身份材料。

## 11. 隐私与安全设计

宿舍地址、房间号和手机号属于敏感场景下的重要个人信息，产品应坚持最小化收集。

建议规则：

- 用户未下单前，商家看不到用户房间号和联系方式；
- 仅接单商家可查看本订单履约所需信息；
- 订单结束一段时间后，对普通商家界面脱敏显示手机号和房间号；
- 平台后台访问敏感数据需分级授权并记录日志；
- 不允许商家导出全量用户联系方式；
- 地址、联系方式不得用于订单履约以外的营销；
- 提供账号注销、地址删除、授权撤回和投诉渠道；
- 明确说明每项信息的用途、保存期限和共享对象；
- 上传的身份和资质材料单独存储，限制访问；
- 云函数校验角色权限，不能只依赖前端隐藏按钮。

宿舍楼层和房间信息还涉及线下人身安全。平台可优先推荐“楼层公共区域交付”或“一楼交付”，由用户自行选择是否提供具体房间号。

## 14. 技术与系统设计建议

### 14.1 推荐架构

基于当前微信云开发项目，可采用：

- 微信小程序：购买者端和商家端；
- 云数据库：用户、店铺、商品、订单等业务数据；
- 云函数：身份鉴权、下单、库存锁定、订单状态流转、审核和风控；
- 云存储：商品图、店铺图、资质材料和投诉凭证；
- 定时任务：订单接单超时、自动完成、库存释放、资质到期提醒；
- 独立Web运营后台：平台审核和管理；
- 日志和监控：异常告警、云函数错误、慢请求、库存不一致检查。

### 14.2 必须放在云函数中的操作

以下操作不能由小程序前端直接可信地完成：

- 创建订单并锁定库存；
- 计算订单金额；
- 判断服务范围；
- 接单、拒单和订单状态迁移；
- 恢复库存；
- 修改商品库存；
- 商家身份和权限校验；
- 审核与封禁；
- 统计销量和成交额。

### 14.3 一致性要求

- 下单、库存锁定和订单创建应在事务中完成；
- 接单/取消必须校验当前状态，避免重复操作；
- 每个状态变更接口要支持幂等；
- 订单号全局唯一；
- 库存变化必须有流水；
- 定时任务重复执行不能重复扣减或恢复库存。

## 15. 运营方案

### 15.1 冷启动

建议采用“单校区、单宿舍区、楼栋渗透”的方式：

1. 找到3～5名稳定的首批商家；
2. 给出统一的选品建议和价格区间；
3. 为每个楼栋制作专属二维码；
4. 通过宿舍群、校园社群和线下海报引导使用；
5. 首期重点考核履约速度和缺货率，而不是店铺数量；
6. 对订单多但供给少的楼栋定向招募商家。

### 15.2 商家运营

- 新商家开店清单；
- 热销选品榜；
- 低库存提醒；
- 营业时间建议；
- 价格异常提示；
- 差评整改；
- 违规培训；
- 月度优秀店铺；
- 长期不营业店铺自动降权。

### 15.3 用户增长

在不接入在线支付的阶段，不建议做复杂红包。可以优先使用：

- 收藏店铺；
- 最近购买一键复购；
- 店铺上新提醒；
- 楼栋热销榜；
- 商家自行提供线下赠品；
- 邀请同楼用户，但避免过度诱导分享；
- 校园活动和社团合作。

## 16. 商业模式

首期建议以验证需求为主，不急于收费。形成稳定订单后可考虑：

1. **商家工具订阅费**：高级数据、批量商品、智能补货等；
2. **店铺推广位**：楼栋内推荐和搜索排序，但必须标识推广；
3. **校园供应链服务**：为商家提供正规供货和集中采购；
4. **品牌推广**：零食品牌校园试吃和新品推广；
5. **订单技术服务费**：需要在支付、合同、税务和平台规则成熟后再评估；
6. **校园区域服务商模式**：由校内运营人员负责商家拓展和管理。

如果平台未来接入在线支付、抽佣和分账，产品、资质、结算、退款、发票、税务及平台责任都会明显增加，应单独立项设计。

## 19. MVP验收标准

首个可用版本至少满足：

1. 用户可以按店铺名称搜索，并可通过商家分享卡片直达指定店铺；
2. 用户可以将商品加入购物车并提交线下付款订单；
3. 并发下单不会造成库存为负；
4. 商家可以接单、拒单、配送和完成订单；
5. 订单取消或超时后库存能够正确恢复；
6. 商家可以创建分类、商品、价格、图片和库存；
7. 平台可以审核和暂停店铺；
8. 平台可以查询订单并处理投诉；
9. 非商家无法调用商家接口；
10. 一个店铺不能查看其他店铺订单；
11. 用户地址和联系方式仅在履约必要范围内展示；
12. 所有库存和订单关键操作都有日志。

## 20. 主要风险与应对

| 风险 | 可能后果 | 建议措施 |
|---|---|---|
| 食品经营资质不明确 | 商家或平台被投诉、处罚 | 限定品类、实名和资质审核、咨询当地监管部门、保留进货凭证 |
| 学校不允许宿舍经营 | 店铺无法持续运营 | 试点前确认学校和宿管规则，优先争取校方合作 |
| 食品过期或来源不明 | 食品安全事故 | 仅售正规预包装食品、记录来源、到期提醒、抽检和举报机制 |
| 无在线支付导致跑单 | 商家损失、库存占用 | 接单超时、取消限制、风险用户机制、订单确认和黑名单申诉 |
| 房间号和手机号泄露 | 骚扰和安全事件 | 最小化收集、接单后可见、完成后脱敏、后台分级权限 |
| 夜间配送产生人身安全问题 | 纠纷或安全事故 | 限定同楼服务、推荐公共区域交付、设置最晚营业时间和紧急投诉 |
| 商家库存不准 | 大量拒单和体验下降 | 原子锁库存、低库存提醒、盘点、库存流水 |
| 平台不收款但被认为担保 | 争议责任不清 | 明确平台角色、线下付款提示、交易规则和投诉处理边界 |
| 恶意竞争或刷差评 | 商家流失 | 仅完成订单可评价、异常行为识别、申诉机制 |
| 微信审核或类目资质问题 | 小程序无法发布 | 在开发前确认主体类型、服务类目、经营内容与所需资质 |

## 21. 上线前必须确认的事项

以下内容应作为项目上线前置条件，而不是上线后的补救项：

- 小程序注册主体采用企业、个体工商户还是其他主体；
- 微信小程序应选择的服务类目及所需材料；
- 试点地区对网络食品交易、预包装食品销售、学生个人经营的具体要求；
- 平台作为交易撮合方需要承担的商家实名、资质审查、信息保存和投诉处理责任；
- 学校、校区及宿管是否允许在宿舍内储存、销售和配送商品；
- 允许和禁止经营的商品清单；
- 经营者的进货查验、储存条件和保质期管理要求；
- 用户协议、隐私政策、商家协议、交易规则和投诉规则；
- 个人信息收集清单及小程序隐私保护指引；
- 商家实名、许可/备案信息至少每6个月复核的流程；
- 商家登记与资质审查档案至少保存2年的存储方案；
- 网络食品订单自交易完成起至少保存3年的存储方案；
- 食品安全管理人员、风险管控清单、违法处置与监管报告机制；
- 食品安全事故、用户受伤、欺诈等突发事件处理预案。

## 22. 最终建议

这个项目的关键不是先做大量功能，而是先验证一个非常具体的闭环：

> 同一栋宿舍中，一名合规、稳定的学生商家能否在5分钟内接单，并在15～20分钟内把一笔低客单价订单可靠地交付给另一名学生。

因此，首期产品设计应坚持：

1. **范围小**：单校区、少量楼栋、有限品类；
2. **履约优先**：接单速度、库存准确和配送成功率优先于营销；
3. **规则清楚**：线下付款、取消、投诉和平台责任边界要明确；
4. **安全合规**：商家、商品、食品、隐私和校园管理都要在开发初期考虑；
5. **架构可扩展**：订单状态、库存流水、角色权限和校园层级从第一版就正确设计。

如果MVP能够稳定达到较高接单率、较低缺货率，并产生明显复购，再逐步增加供应链、营销、付费商家工具以及在线支付能力。
